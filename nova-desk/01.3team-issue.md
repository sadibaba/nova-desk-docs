Samajh gaya — masla clear hai, aur ye load/stress ka issue nahi hai, ye ek **code bug** hai jo har single request pe fail hoga, chahe 1 user ho ya 50.

## Root cause

`team_Service.js` mein `getTeamStats()` dekhein:

```js
static async getTeamStats(teamId) {
  const TeamTask = mongoose.model('TeamTask');       // ⚠️
  const TeamChannel = mongoose.model('TeamChannel');
  const TeamMessage = mongoose.model('TeamMessage'); // ⚠️
  ...
}
```

`mongoose.model('TeamTask')` — **bina schema pass kiye** — sirf tab kaam karta hai jab `TeamTask` model kahin aur pehle se register ho chuka ho (matlab kisi file ne `mongoose.model('TeamTask', schema)` ya us model file ko import kiya ho, taake mongoose ke internal registry mein woh naam maujood ho).

Maine poore uploaded backend mein grep kiya:

```
TeamTask     → sirf yehi 2 lines mein reference hai (team_Service.js)
TeamMessage  → sirf yehi 2 lines mein reference hai (team_Service.js)
```

Matlab in dono models ko **kahin bhi import nahi kiya ja raha** app ke kisi aur file mein — is wajah se mongoose ki registry mein `TeamTask` aur `TeamMessage` naam ke models exist hi nahi karte (jab tak koi aur module unhe load na kare).

Jab `mongoose.model('TeamTask')` kisi unregistered naam ke sath call hota hai, ye **synchronously throw** karta hai:

```
MissingSchemaError: Schema hasn't been registered for model "TeamTask".
Use mongoose.model(name, schema)
```

Ye throw `Promise.all` tak pohanchne se pehle hi ho jata hai — is liye `TeamTask?.countDocuments(...)` wala optional-chaining bhi kaam nahi aata (kyunki error `mongoose.model()` line pe hi throw ho jata hai, us line se pehle jahan `?.` lagi hai).

Ye error `team_controller.js` ke catch block mein pakdi jaati hai:

```js
} catch (error) {
  console.error("getTeamStats error:", error);
  res.status(500).json({ success: false, error: error.message });
}
```

Isi liye **har** `/stats` request 500 return karti hai — 3425/3425 fail (0%), aur k6 ka `response` check yehi expect kar raha tha ke status 200 + valid data mile, jo kabhi nahi milta.

## Fix

`team_Service.js` mein `getTeamStats` ko is tarah resilient bana dein:

```js
static async getTeamStats(teamId) {
  const safeCount = async (modelName, filter) => {
    try {
      const Model = mongoose.model(modelName);
      return await Model.countDocuments(filter);
    } catch {
      return 0; // model registered nahi, ya abhi feature nahi bana, to silently 0
    }
  };

  const [memberCount, taskCount, channelCount, messageCount] = await Promise.all([
    TeamMember.countDocuments({ team: teamId, status: 'active' }),
    safeCount('TeamTask', { team: teamId }),
    safeCount('TeamChannel', { team: teamId }),
    safeCount('TeamMessage', { team: teamId })
  ]);

  return { memberCount, taskCount, channelCount, messageCount };
}
```

Behtar aur permanent fix ye hai ke `TeamTask` aur `TeamMessage` ko top pe actual model file se **explicitly import** karein (jese `TeamChannel` already ho raha hai `team_controller.js` mein), taake ye kabhi bhi kisi import-order pe depend na kare:

```js
import TeamTask from '../../task/models/team_task.model.js';      // apna actual path check karlein
import TeamMessage from '../../chat/models/team_message.model.js'; // apna actual path check karlein
```

Agar ye model files project mein exist hi nahi karte abhi tak (feature incomplete hai), to `safeCount` wala fallback use karlein — stats endpoint chalta rahega, bas un fields mein `0` aayega jab tak wo feature complete na ho.

Ek chhoti si cheez aur nazar aayi (blocking nahi, but note karlein): `getTeamStats` controller mein `metadata: stats` use kar raha hai jabke baqi sab controllers (`listUserTeams`, `searchTeams`, `getUserInvites`) `data: result` use karte hain — dono mein consistency nahi hai. Ye check karlein `core/success.response.js` mein `SuccessResponse` class kaunsa param name (`data` ya `metadata`) actually response body mein daalti hai, warna aapka data silently drop ho sakta hai response se.
